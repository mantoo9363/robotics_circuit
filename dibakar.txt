## 1. Frontend Architecture & The Browser Performance Model

Kyunki hamare paas koi dedicated backend simulation worker nahi hai, browser ka single-threaded **JavaScript Event Loop** ek hi waqt par ye 5 heavy tasks handle kar raha hai:
```
┌────────────────────────────────────────────────────────────────────────┐
│                   Browser Main Thread (Single Thread)                  │
├────────────────────────────────────────────────────────────────────────┤
│ 1. User Interactions (Mouse Drag, Zoom, Pan, Typing in Monaco Editor)  │
│ 2. Simulation Tick Generation (setInterval / requestAnimationFrame)     │
│ 3. AST Execution & Electrical Graph Traversal (41 Transformers)        │
│ 4. React Component Tree Reconciliation & DOM Commit                    │
│ 5. SVG Layout, Paint & Compositing (60 FPS Target)                     │
└────────────────────────────────────────────────────────────────────────┘
```
**Budget**: Agar in 5 tasks ka total execution time **16.6ms** se zyada hota hai, toh browser frames drop karta hai (lag/stuttering) aur mobile/laptop devices par CPU thermal throttling aur battery drain shuru ho jata hai.

## 2. Area 1: Simulation Loop & Frame Pipeline

### 🔴 Identified Bottlenecks:
1. **Unconditional 41-Transformer Loop** ([`framePipeline.ts:62-113`](file:///Users/lightyagami/work/Robotics_Circuit/circuit/src/lib/simulation/framePipeline.ts#L62-L113)):
   * Har tick par pipeline **41 transformers** ko `Array.reduce` me chalati hai (e.g. `applyGasSensor`, `applyFlexSensor`, `applySoilMoisture`, `applyFunctionGenerator`, `applyTiltSensor`, `applySevenSegment`).
   * Chahe canvas par sirf 1 ESP32 aur 1 LED ho, baaki 39 transformers tab bhi run hokar `nodes.filter()` aur `find()` array traversals execute karte hain.
2. **Deep Object Cloning on Every Tick**:
   * Har transformer `components = { ...frame.components }` aur `component = { ...prev }` karta hai.
   * Ek 30-component circuit me 41 transformers har second **50,000+ short-lived JavaScript objects** allocate karte hain. Isse Garbage Collector (GC) har 2-3 second me **Major GC Pause** trigger karta hai, jisse UI freeze hoti hai.
3. **Simulation Session Leaks Across Restarts**:
   * Stop ➔ Start simulation karne par static maps (`neopixelStates`, `sessions`, `serialSessions`) agar clean wipe na hon, toh purani session memory me lingering rehti hai.

### 🟢 Solution & Optimization:
* **Dynamic Active-Transformer Registry**: Simulation start hote hi canvas ke active component types ka ek `Set<string>` banaya jayega. Sirf wahi transformers pipeline me bind honge jinke components canvas par physically present hain.
* **In-Place Frame Mutation Buffer**: Double-buffered frame structure use kiya jayega jahan `Frame A` aur `Frame B` alternate honge, zero new object allocation per tick.

## 3. Area 2: Zustand State Store, Selectors & Undo/Redo

### 🔴 Identified Bottlenecks:
1. **Non-Primitive Selectors in React Nodes**:
   * [`Neopixel.tsx:9`](file:///Users/lightyagami/work/Robotics_Circuit/circuit/src/components/nodes/Neopixel.tsx#L9): `useCircuitStore((s) => s.simulationFrame?.components[props.id])`
   * [`ESP32Node.tsx:33`](file:///Users/lightyagami/work/Robotics_Circuit/circuit/src/components/nodes/ESP32Node.tsx#L33): `useCircuitStore((state) => state.arduinoPins)`
   * [`BaseCircuitNode.tsx`](file:///Users/lightyagami/work/Robotics_Circuit/circuit/src/components/nodes/BaseCircuitNode.tsx): Poore `simulationFrame` ko listen karta hai.
   * Result: Jab tick chalta hai, React Flow canvas ke **saare 46 node types ek sath re-render** trigger karte hain chahe unka voltage ya state 0V hi kyun na ho.
2. **Undo/Redo History Bloat**:
   * Agar user wire connect/move karta hai, canvas state history stack me poora snapshot store hota hai. Agar simulation running ke waqt simulation telemetry state history me leak ho jaye, toh memory consumption 500MB+ pahunch sakti hai.

### 🟢 Solution & Optimization:
* **Zustand Fine-Grained Atomic Selectors + `useShallow`**:
  * Har node sirf apne primitives (`brightness`, `voltage`, `burnt`, `color`) par listen karega.
* **State Decoupling**: Static circuit topology (`nodes`, `edges`, `properties`) ko dynamic runtime telemetry (`voltages`, `pins`, `currents`) se alag store me split kiya jayega.

## 4. Area 3: React Flow Canvas, SVG Graphics & DOM Rendering

### 🔴 Identified Bottlenecks:
1. **Complex SVG Filter Overheads (Drop Shadows & Gaussian Blurs)**:
   * [`Neopixel.tsx:45`](file:///Users/lightyagami/work/Robotics_Circuit/circuit/src/components/nodes/Neopixel.tsx#L45): `filter: 'blur(5px)'` + radial gradients + multiple overlapping SVG `<path>` elements.
   * Browser GPU ko har 16ms par heavy filter effects re-rasterize karne padte hain.
2. **Continuous Edge Bezier Recalculation**:
   * Jab canvas par koi element highlight hota hai, React Flow edges ko re-compute karta hai.
3. **DOM Layout Thrashing**:
   * Dynamic tooltips, badges, aur warning modals inline CSS styles recalculate karte hain.

### 🟢 Solution & Optimization:
* **CSS Hardware Acceleration**: Glowing elements par `will-change: transform, opacity` aur `transform: translateZ(0)` use karna taaki GPU dedicated layer composite kare.
* **Component-Level `React.memo` with Custom Comparators**: Components tabhi render honge jab unka visual output actually change ho.

## 5. Area 4: Electrical Solver, Conductive Graph & Breadboard

### 🔴 Identified Bottlenecks:
1. **Redundant Graph Re-construction** ([`graph.ts:43-100`](file:///Users/lightyagami/work/Robotics_Circuit/circuit/src/lib/circuit/graph.ts#L43-L100)):
   * Breadboard me 30 columns $\times$ 5 rows + rails ke loop se har call par hundreds of `Set<string>` aur `Map` create hote hain.
   * Multiple transformers ek hi frame tick me 5 se 10 baar graph rebuild karte hain.
2. **String Key Allocation in BFS Traversals**:
   * `getReachableGraphNodes` me `${edge.source}:${edge.sourceHandle}` jaise hazaron dynamic strings per second bante hain aur garbage collect hote hain.

### 🟢 Solution & Optimization:
* **Graph Versioning Cache**: Graph sirf tab rebuild hoga jab `topologyVersion` badlega (wire add, wire remove, component drag-drop, switch toggle). Normal simulation run ke waqt graph **100% cached** rahega (CPU time drops from 8ms ➔ 0.05ms).
* **Interned String Handles / Numeric Pin IDs**: Handle keys ko pre-allocated enum/integer IDs me convert karna.

## 6. Area 5: C++ & MicroPython Code Parsing Engine

### 🔴 Identified Bottlenecks:
1. **Un-memoized Regex Execution in Hot Loop**:
   * `cppPatterns.ts`, `cppLcd.ts`, `cppUltrasonic.ts`, `cppNeopixel.ts` har frame par raw C++ string par:
     * `stripCppComments()`
     * `stripCppIncludes()`
     * `extractFunctionBody()`
     * `parseCppConstants()`
     * Multi-level Regex matching chalate hain.
   * Jabki user ka code editor me change hi nahi hua hota!
2. **Redundant Condition Re-evaluation**:
   * Dynamic variables har tick par fresh `new Function(...)` compile karte hain.

### 🟢 Solution & Optimization:
* **Code Hash AST Cache (`codeHash`)**:
  * Code string ka fast numeric hash store hoga.
  * Static structures (pin modes, strip instances, LCD addresses, ultrasonic pins) **sirf code edit hone par 1 baar compile** honge.
  * Runtime frame ticks sirf pre-compiled AST me pin values inject karke evaluate karega (< 0.1ms execution).

## 7. Area 6: Serial Monitor, Telemetry & High-Frequency I/O

### 🔴 Identified Bottlenecks:
1. **Unbounded Serial Buffer Growth**:
   * Agar code me `while(true) { Serial.println("data"); }` ho bina delay ke, toh `consoleLogs` array me 100,000+ strings bhar jaati hain, jisse browser tab crash / "Out of Memory" ho jata hai.
2. **Serial Terminal DOM Thrashing**:
   * Har naye log par poora Terminal component re-render hota hai aur auto-scroll calculate karta hai.

### 🟢 Solution & Optimization:
* **Circular Ring Buffer**: Serial logs ko fixed size buffer (e.g. max 1,000 lines) par clamp karna.
* **Throttled Virtualized Terminal**: Terminal UI me DOM virtualization aur 60Hz throttled batching lagana taaki high-speed logs bhi browser ko freeze na karein.

## 8. Area 7: Component Status & Warning Badges

### 🔴 Identified Bottlenecks:
* [`componentStatus.ts`](file:///Users/lightyagami/work/Robotics_Circuit/circuit/src/utils/componentStatus.ts): Har tick par circuit ke har individual component ke voltage, forward bias, reverse bias, burnout limits calculate karta hai.
* Agar canvas par 50 components hain, toh 50 diagnostic checks per frame run hote hain, creating many intermediate status summary objects.

### 🟢 Solution & Optimization:
* **Dirty Flag Diagnostic Engine**: Status calculation sirf un components ke liye run hoga jinka voltage ya pin state pichhle frame se change hua ho.

## 9. Area 8: Web Audio, Motors & Dynamic Animation Subsystems

### 🔴 Identified Bottlenecks:
1. **AudioContext Leak**: Buzzer / Piezo components agar har note par naya `new AudioContext()` banayein, toh browser limit (max 6 active audio contexts) hit ho sakti hai.
2. **Motor RPM Animation Timers**: Servo aur DC Motor visual rotation ke liye multiple independent timers chalana.

### 🟢 Solution & Optimization:
* **Singleton Master Audio Engine**: Poore application ke liye 1 shared audio context with master volume limiter.
* **Unified Animation Clock**: Single `requestAnimationFrame` loop jo saare motors, LEDs, aur displays ko sync me render kare.
